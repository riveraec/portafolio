Case study

eventos-api — webhooks sin duplicar

Problema
Un emisor puede reenviar el mismo evento. Si la API inserta otra vez, hay doble efecto (pago/aviso contado dos veces).
Decisión
Clave natural id + SQLite: primer POST → 201; el mismo id → 200 con el registro ya guardado. Validación con Zod y tests HTTP.
Resultado
Reprocesar es seguro. Misma idea de idempotencia que en el ETL batch. CI con npm test en cada push.

Hilo con etl-reportes: webhook y batch, mismo criterio (reprocesar ≠ duplicar).
